# データベースと検索インデックス

## データの責務

PostgreSQLを構造化データの原本とする。会話履歴、タスク、ユーザー設定、実行履歴、Memoryメタデータ、および検索インデックスとの対応IDを保存する。

Vector DB（Qdrantまたはpgvector）は意味検索のためのインデックスとする。Embedding、文書チャンク、類似度検索に必要なデータを保持する。Vector DBだけを正本として扱わず、原本を復元できない状態を作らない。同じ情報を目的なく二重管理しない。

## 実装境界

- SQLModelは永続化モデルとDBアクセスのために利用する。入出力の要件、公開契約、検証要件が異なる場合はDBモデルとスキーマを分離する。
- RepositoryはFeature所有データの保存・取得・検索を担い、ユースケース判断やAPI/CLIの型を持ち込まない。
- Featureは自身のデータを所有する。他Featureのテーブルを直接操作せず、所有Featureの公開操作を使う。
- トランザクション境界は一つのユースケースで原子的に確定できるPostgreSQL操作に置く。Vector DBを含む複数ストアの完全な分散トランザクションは前提にしない。

## 整合性と変更

PostgreSQLの原本IDを、Vector DB側のpoint/documentと対応付ける。保存・更新・削除時は、原本の状態とインデックス更新の成否を記録し、失敗時に再試行または再インデックスできる状態を保つ。再インデックスは原本から再構築できる操作として設計する。

スキーマ変更はmigrationで追跡し、アプリケーション起動時の暗黙変更に依存しない。migrationの導入方法と実行手順は、実際のプロジェクト設定に合わせて決める。
